# Phase 7.3 — Apply의 항목별 호출을 묶는다

**요약.** `_apply_add`가 항목마다 `file_ops.copy_files()`와 `adapter.write_index()`를
부르던 것을 묶었다. **400게임 Apply가 20.50s → 1.20s(17배).** 관찰 가능한 동작 —
어떤 항목이 성공/실패하고 무엇이 되돌려지는가 — 은 그대로다.

파이썬 331개(신규 8개), Playwright 51개 전부 통과.

---

## 1. 무엇이 느렸는가 (Phase 7.2 Hardening의 측정 결과)

| 게임 수 | Apply (이전) |
|---|---|
| 100 | 4.55s |
| 200 | 9.67s |
| 400 | 20.50s |

선형이되 **항목당 약 50ms**. 그 50ms를 갈라 보니(200게임 9.79s 기준):

| 복사 호출만 제거 | **1.98s** |
|---|---|
| write_index만 제거 | 7.87s |

**복사가 80%, `write_index`가 20%.** Robocopy 프로세스가 항목마다 새로 뜨는 비용이
진짜 병목이었다.

---

## 2. 세 단계로 나눴다

```
_apply_adds()
  ├─ 준비   : 항목마다 복사할 쌍을 계산만 한다 (파일 안 건드림)
  ├─ 복사   : 25개씩 묶어 file_ops.copy_files() 호출
  └─ 기록   : System 단위로 adapter.write_index() 한 번
```

### 왜 전부 한 번에 묶지 않았는가

복사는 Apply에서 가장 오래 걸리는 구간이다. 통째로 묶으면 그 동안 **진행률이 멈춰
사용자는 앱이 죽은 것으로 본다.** 25개 묶음이면 프로세스 기동이 25분의 1로 줄면서도
진행률은 계속 움직인다. 테스트가 "묶음이 하나뿐이면 안 된다"를 고정한다.

`write_index`는 묶음이 하나여도 된다 — gamelist.xml 하나를 여는 일이라 오래 걸리지
않고, System 단위가 Adapter 계약 1이 요구하는 단위이기도 하다.

---

## 3. 되돌리기 정책 — **바꾸지 않았다**

리뷰가 "실패/rollback 정책 고정"을 함께 요구했는데, 확인해 보니 정책은 이미
`tests/test_plan_recovery.py`에 명시적으로 박혀 있었다(Phase 3 hardening에서 정한 것).
그래서 **새로 정하지 않고 그대로 지켰다.**

| 실패 지점 | 정책 | 이번에 바뀐 것 |
|---|---|---|
| 복사 | 그 항목만 FAILED. **그 항목이 이번에 새로 만든 파일만** 되돌린다 | 없음 |
| 메타데이터 쓰기 | 복사한 파일을 되돌리고 FAILED | 대상이 그 System의 항목 전체로 늘어남 |
| media 링크 쓰기 | PARTIAL, 파일은 유지 | 없음 (Phase 7.1에서 정함) |

### 묶었는데 실패 단위가 그대로일 수 있는 이유

`copy_files()`가 **목적지별 성공 여부**를 돌려준다. 그래서 호출을 묶어도 어느 항목이
실패했는지 정확히 알 수 있고, 되돌리는 것은 그 항목의 파일뿐이다.
**호출을 묶는 것과 실패를 묶는 것은 별개다** — 이 구분이 이번 작업의 핵심이다.

### 메타데이터 실패의 대상이 늘어나는 것에 대해

항목마다 쓰던 때는 실패한 항목만 되돌렸다. 이제는 그 System의 항목 전체가 대상이다.
그래도 결과는 같다 — 디스크/권한 문제로 한 항목이 실패하면 나머지도 전부 실패했을
것이고, 각각 되돌려져 결국 같은 상태가 된다.

### media 링크만 정책이 다른 이유

- **메타데이터가 없으면** 그 ROM은 gamelist에 없는 유령 파일이 된다. 다음 스캔에서
  이상하게 보이고 다음 Apply가 충돌로 막힌다 → 되돌리는 게 낫다.
- **media 링크만 없으면** 항목은 이미 gamelist에 있고 파일도 유효하다. 다시 시도하면
  경로만 채우면 된다 → 되돌리면 오히려 복사를 다시 해야 한다.

## 4. 결과

| 게임 수 | 이전 | 이후 | |
|---|---|---|---|
| 100 | 4.55s | **0.34s** | 13배 |
| 200 | 9.67s | **0.60s** | 16배 |
| 400 | 20.50s | **1.20s** | **17배** |

호출 횟수(400게임): `copy_files` 400회 → 16회, `write_index` 400회 → 1회.

media까지 포함한 실제 규모:

| | Apply |
|---|---|
| 1,000 게임 + media 1,332개 | 12.36s |
| 5,000 게임 + media 6,666개 | 61.34s |

이제 남은 시간은 **실제 파일 I/O**다. 프로세스 기동 몫이 아니다.
