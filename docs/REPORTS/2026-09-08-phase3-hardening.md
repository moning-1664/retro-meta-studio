# Phase 3 Hardening — 수정 내역과 확인이 필요한 결정

**요약.** Phase 3 코드 리뷰 피드백의 P0/P1 항목을 모두 반영했다. 핵심은 "정상 상황에서는
잘 되는데 예외 상황에서 DB와 실제 파일 상태가 서로 달라지는 것"을 없애는 것이었고,
파일 엔진의 성공 판정, 목적지 충돌 정책, Storage 이동의 트랜잭션성, ADD 실패 롤백,
Cache 동기화, DELETE 의미를 고쳤다. 실패 주입 테스트 12개를 새로 추가해 전체 163개가
통과한다. 다만 **아래 §확인이 필요한 결정 3건**은 추천안으로 먼저 구현했으니 선택해주기 바란다.

---

## 1. 고친 것

### P0-① 파일 엔진의 성공 판정 (피드백 §11, §12)

`dest.exists()`만으로 성공을 판정하고 있었다. **목적지에 원래 파일이 있었고 이번 복사가
실패한 경우에도 참**이 되므로 실패를 성공으로 보고했다. 이동에서는 더 위험해서, 원본을
지워도 된다고 오판하면 파일이 두 곳에 남거나 사라진다.

이제 복사는 `크기 일치 + 수정 시각 일치`(복사 도구가 타임스탬프를 보존하는 성질을 이용),
이동은 여기에 더해 **원본이 실제로 사라졌는지**까지 확인한다. 두 엔진(Robocopy /
네이티브 워커)에 같은 계약 테스트를 돌려 동일하게 동작함을 확인했다.

### P0-② 목적지 충돌 정책 (피드백 §2, §3, §10)

`같은 크기 → 물리 증가 0`으로만 계산하고 Apply에서는 그냥 덮어쓰고 있었다. **`같은 이름
+ 같은 크기 + 다른 내용`은 ROM 관리에서 흔하다.**

용량 계산과 충돌 판정을 분리했다.

| 목적지 상태 | 처리 |
|---|---|
| 없음 | 복사 (delta +크기) |
| 크기·수정시각 모두 일치 | 이미 같은 파일로 보고 건너뜀 (delta 0, 묻지 않음) |
| 그 외 (크기 다름 / 크기 같고 시각 다름) | **충돌** — 사용자가 결정 (delta 0) |

충돌은 `skip` 또는 `overwrite`로 해결하며, 덮어쓰기를 고르면 용량이 **차이만큼**만
계산된다(500MB를 700MB로 덮으면 +200MB). 미해결 충돌은 Apply가 아예 건드리지 않는다.

Storage 이동도 대상에 같은 이름의 파일이 있으면 이동을 시작하지 않는다.

### P0-③ Storage 이동 트랜잭션과 복구 (피드백 §1)

가장 심각한 문제였다. 파일 이동 성공 후 `registry.move_system()`이 실패하면
`파일은 External, Registry는 Internal`이 되어 앱이 ROM을 찾지 못한다. 부분 이동도
마찬가지로 위험했다.

이제 이동과 Registry 갱신을 하나의 논리적 트랜잭션으로 다룬다.

```
검증 → 충돌 검사 → 이동 → 검증 → Registry 갱신
   ↑ 어느 단계가 실패하든 이미 옮긴 파일을 원래 자리로 되돌린다
```

되돌리기까지 실패하면 단순 실패가 아니라 `partial`로 표시해 사용자가 손대야 함을 알린다.

### P0-④ ADD 실패 롤백 (피드백 §5)

파일 복사는 성공했는데 gamelist 기록이 실패하면 `ROM 있음 / gamelist 없음`이 남았다.
이제 **이번에 새로 만든 파일만** 되돌린다(원래 있던 파일은 건드리지 않는다). 되돌리기가
실패하면 `partial` 상태로 구분한다.

### P1-⑤ Cache 동기화 (피드백 §7, §8)

Apply 후 전체 Full Scan을 돌고 있었다. 정확하지만 10,000개짜리 Collection에서 게임 하나를
지울 때마다 전체를 훑는 것은 감당이 안 된다. 이제 **Apply가 건드린 System만** 다시 읽는다.

### P1-⑥ DELETE 의미 (피드백 §6)

ROM/Media만 지우고 gamelist 항목을 남겨서, 다음 스캔에서 metadata-only 항목으로
되살아난 것처럼 보였다. 이제 게임 삭제는 **ROM + Media + gamelist 항목**을 모두 없앤다.
`<folder>`처럼 우리가 해석하지 않는 요소는 그대로 보존한다.

### P1-⑦ DELETE 재검증 (피드백 §9)

Cache 행 존재만 확인했다. Plan을 만든 뒤 외부에서 ROM이 교체되었어도 통과해서, 사용자가
의도하지 않은 파일을 지울 수 있었다. 이제 실제 파일의 크기와 수정 시각이 Cache와 같은지
확인하고, 다르면 `외부에서 변경됨`으로 막는다.

### ④ Apply 결과 표시 (피드백 §4)

실패 항목이 Plan에 남는다는 사실이 UI에 드러나지 않았다. 이제 결과에
`적용 N · 실패 N · 일부만 반영 N · 충돌로 건너뜀 N — M개가 Plan에 남아 있습니다`를
표시하고, 하단 바에 충돌/실패 배지를 상시 노출한다.

## 2. 확인이 필요한 결정

### (1) "같은 파일" 판정 기준 — 지금은 시각까지 정확히 일치할 때만

추천안으로 **크기 + 수정 시각 정확 일치**를 채택했다. 복사 도구가 타임스탬프를 보존하므로
이 앱이나 다른 도구가 복사해둔 파일은 정확히 일치한다.

- **장점**: 확신할 수 없으면 절대 덮어쓰지 않는다.
- **단점**: 다른 경로로 받은 같은 ROM(내용은 동일한데 시각이 다름)이 충돌로 잡힌다.
  그래서 "모두 건너뛰기 / 모두 덮어쓰기" 일괄 처리를 넣었다.

**대안**: 크기가 같을 때 해시(SHA256)를 계산해 내용까지 확인. 확실하지만 4GB짜리 ROM
수백 개면 수십 분이 걸린다. 사용자가 명시적으로 요청할 때만 도는 "내용 비교" 버튼으로
넣는 것도 가능하다.

**질문: 지금 기준을 유지할까, 아니면 "내용 비교" 버튼을 추가할까?**

### (2) 삭제를 셋으로 나눌지

피드백은 `Delete Game` / `Remove ROM`(metadata 유지) / `Cleanup`(고아 정리) 세 가지 분리를
권했다. 지금은 가장 흔한 **Delete Game**(ROM+Media+gamelist 전부 제거)만 구현했다.

**질문: `Remove ROM`(ROM만 지우고 메타데이터는 남김)을 지금 추가할까, Cleanup과 함께
나중에 할까?**

### (3) 충돌 해결에 "이름 바꿔 저장"을 넣을지

지금은 `건너뛰기` / `덮어쓰기` 둘뿐이다. 피드백은 `Rename`도 언급했다. 이름 규칙
(`Game (2).iso` 등)을 정해야 하고 gamelist 항목도 새 이름으로 들어가야 해서 파급이 있다.

**질문: 필요한가?**

## 3. 아직 안 한 것 (의도적으로 미룸)

- **Plan identity를 filename에서 ROM/Game identity로 전환** (피드백 §16). Archive/Match가
  본격적으로 들어오는 Phase 5 전에 정리하는 것이 맞다는 피드백 판단에 동의한다.
- **Multi-disc / multi-file ROM의 media 대응** (피드백 §17). 같은 이유로 Phase 5 전.
- **Clipboard의 절대경로 의존** (피드백 §14). MTP(Phase 8) 전까지는 문제되지 않는다.
