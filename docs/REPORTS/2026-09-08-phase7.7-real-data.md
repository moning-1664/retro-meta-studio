**요약.** 사용자의 실제 자료로 스캔을 돌렸다. **테스트 403개가 전부 통과하는
상태였지만, 실제 컬렉션은 40%가 스캔되지 않고 있었다.**

| | 고치기 전 | 고친 후 |
|---|---|---|
| 스캔 결과 | **930 게임** (오류로 중단) | **1,546 게임** (정상 완료) |
| 읽힌 gamelist | 26개 중 17개 | **26개 전부** |

파이썬 356개(신규 10개), Playwright 57개 전부 통과.

## 대상 자료

```
메타데이터 : C:\\Users\\moning\\Downloads\\Backup\\ES-DE_3.1.01312312\\ES-DE
             gamelists 26개 시스템 / 1,539 게임, downloaded_media 14,705개 / 13.87 GB
ROM        : C:\\Games\\ROMs   43개 시스템 / 3,686개 / 182.8 GB
```

ES-DE 표준 배치(메타데이터와 ROM이 분리)라, Collection root를 ES-DE 폴더로 잡고
ROM 폴더를 External Storage로 붙인 뒤 모든 System을 그쪽으로 옮겨 스캔했다. **이 앱이
원래 의도한 사용 방식 그대로**이고, 그 경로가 실제로 동작하는지까지 함께 확인된 셈이다.

스캔은 읽기 전용이고 registry/cache는 임시 폴더에 만들었다 — 실제 자료에는 아무것도
쓰지 않았다.

---

## ① `<alternativeEmulator>` — 9개 시스템 488게임(32%) 유실

ES-DE 3.x가 실제로 쓰는 형태다.

```xml
<?xml version="1.0"?>
<alternativeEmulator>
    <label>Snes9x 2010</label>
</alternativeEmulator>
<gameList>
```

최상위 요소가 **둘**이라 엄밀히는 잘못된 XML이고 `ET.parse`가 *"junk after document
element"* 로 거절한다. 우리 `_parse_file`은 `ParseError`를 삼키고 `None`을 돌려주므로
**그 System의 메타데이터가 통째로 사라졌다.** 26개 중 9개가 이 형태였다
(cps1/cps2/cps3/famicom/gb/gbc/megadrive/psx/sfc).

→ 엄밀한 파싱이 실패하면 임시 루트로 감싸 다시 읽고 `<gameList>`만 꺼낸다.

## ② 이스케이프하지 않은 `&` — famicom 199게임 유실

```xml
<name>캡틴 아메리카 & 어벤저스</name>
```

이건 ES-DE 탓이 아니라 진짜로 깨진 파일이다. 그래도 **한 글자 때문에 199개 항목을
통째로 버리는 것이 더 나쁘다.** 감싸기도 실패했을 때만, 올바른 실체 참조(`&amp;`,
`&#39;`)를 건드리지 않고 맨 `&`만 고쳐 다시 시도한다.

복구는 최선을 다하는 것이지 아무거나 통과시키는 것이 아니다 — 정말 못 읽는 파일은
여전히 빈 결과를 주고 스캔은 계속된다(테스트로 고정).

## ③ 같은 media type 두 개 — **스캔이 죽어서** 8개 시스템 미스캔

```
downloaded_media/nes/covers/Shanghai 1.jpg
downloaded_media/nes/covers/Shanghai 1.png
```

Cache의 `media` 테이블은 `(rom_uid, media_type)`이 기본 키다. 같은 타입이 둘 들어오면
`UNIQUE constraint failed`로 **스캔 전체가 예외로 끝난다.**

media 14,705개 중 이런 ROM은 **단 2개**였는데, 그 둘 때문에 `nes` 이후 8개 시스템이
아예 스캔되지 않았다(nes 201, sfc 72, psx 45, pcengine 27, pcenginecd 22, ps2 23,
psp 26 …). 게다가 작업은 `done: True`로 끝나서 **겉보기에는 성공한 것처럼 보였다.**

→ 스캐너가 타입당 하나만 남긴다. 어느 것을 남길지는 **경로 순서**로 정한다 — 스캔할
때마다 달라지면 Compare가 매번 "다르다"고 말하기 때문이다.

## ④ ES-DE 자체 폴더가 System으로 잡힘

`controllers`, `screensavers`, `temp`가 게임 시스템으로 잡혀 빈 항목이 목록에 떴다.
`RESERVED_DIRS`에 추가했다.

## ⑤ 목업이 실제와 다른 모양을 돌려주고 있었다

`add_external_storage`의 실제 반환은 **storage id 문자열**(`ok(storage_id)`)인데
목업은 객체를 돌려주고 있었다. 지금 UI는 `r.data`를 안 읽어서 드러나지 않았지만,
화면이 `r.data.id`를 읽도록 바뀌면 **테스트만 통과하고 앱에서 깨진다.**

`tests/test_wiring.py`는 이름과 인자 개수까지만 보므로 이 종류는 못 잡는다. 실제
데이터로 돌려 보다 걸렸다.

---

## 왜 테스트가 이걸 못 잡았나

합성 fixture는 **우리가 아는 모양만** 만든다. 위 다섯 가지는 전부 "우리가 모르던
모양"이었다.

- `build_custom_esde_tree()`는 늘 올바른 XML을 쓴다 → ①②를 만들 수 없다.
- fixture는 타입당 media 파일을 하나만 만든다 → ③을 만들 수 없다.
- 목업은 사람이 손으로 쓴 것이라 실제 반환 모양과 어긋날 수 있다 → ⑤.

그래서 이번에 찾은 모양들을 `tests/test_real_world_esde.py`에 **작은 fixture로 옮겨
왔다.** 실제 경로를 테스트가 직접 보게 하지는 않는다 — 182GB이고 그 PC에만 있으며,
쓰기 경로가 실수로 실제 자료를 건드리면 되돌릴 수 없다.

수정을 임시로 되돌려 보니 **10개 중 7개가 실패**한다(Phase 7.1에서 정한 확인 절차).
