# Phase 7.2 Hardening — 변환의 마지막 10% 검증

**요약.** 리뷰가 지목한 9개 항목을 처리했다. 가장 먼저 보라고 한 ①②가 정확했다 —
`_items_from()` 경계에서 **실제 버그가 하나 나왔고, 그것 때문에 Frontend 간 Convert가
아예 실패하고 있었다.**

그리고 벤치마크 결과가 **내가 앞서 보고한 우선순위를 뒤집었다**(§8).

파이썬 323개(신규 18개), Playwright 51개 전부 통과.

---

## ① frontend_raw가 target으로 넘어가 Convert를 깨뜨리고 있었다 (실제 버그)

`frontend_raw`는 Frontend마다 **모양이 다르다.**

```
ES-DE    : {"tag": "playcount", "text": "17", "attrib": {}}
Pegasus  : {"key": "sort-by",   "value": "Final Fantasy 10"}
```

Convert가 source의 `frontend_raw`를 그대로 실어 보내고, target Adapter가 그것을
되살리려다 깨졌다.

```
FFX.iso: Metadata 기록 실패: 'key'      ← Pegasus가 item["key"]를 찾다가 KeyError
apply: applied=0 failed=1
```

즉 **미지 태그가 하나라도 있는 항목은 Frontend 간 Convert가 통째로 실패했다.** Phase 7.2의
테스트가 이걸 놓친 이유는 `build_custom_esde_tree()`가 미지 태그를 만들지 않기 때문이다 —
fixture가 현실보다 깨끗했다.

### 고친 방식 — 값이 자기 출처를 스스로 밝히게 했다

```python
RAW_FRONTEND_KEY = "_frontend"     # frontend_raw 안에 들어가는 출처 표시
adapter.tag_raw(raw)               # to_common()의 마지막에 붙인다
adapter.raw_is_mine(raw)           # 소비하는 쪽에서 판정한다
```

출처를 **값 안에** 넣었기 때문에 Clipboard 핸드오프 파일이나 Archive DB를 거쳐도 함께
따라간다. 스키마를 늘리지 않고 어디서든 "이건 내 것인가"를 물을 수 있다.

소비하는 두 곳을 고쳤다.

- `_apply_add` — 남의 것이면 통째로 버리고, 내 것이면 `strip_location_raw()`만 적용.
- `archive/service.py::to_collection` — Archive의 raw는 그것을 올린 Collection의 것이라
  같은 판정이 필요하다. (이 경로도 같은 위험을 갖고 있었다.)

**출처 표시가 없으면 내 것으로 본다.** 예전에 저장된 값에는 표시가 없는데, 표시가 없다고
버리면 계약 2를 어기는 쪽이 된다.

방어도 하나 넣었다 — Pegasus의 `from_common`이 모양이 다른 항목을 만나도 건너뛴다.
호출부가 걸러주는 것이 정상이지만, 여기서 KeyError로 Apply 전체가 죽는 일은 없어야 한다.

## ② media 경로 해석 — 정상, 다만 이름이 오해를 부른다

`cache`의 media 항목 키는 `rel_path`인데 **실제로는 절대 경로**가 들어 있다
(`scanner.py`가 `m.path`를 그대로 넣는다). Convert가 그것을 provider에 그대로 넘겨도
문제없이 열린다 — 테스트로 고정했다(`is_absolute()` + `exists()`).

이름을 바꾸는 것은 cache 스키마와 clipboard 핸드오프 포맷을 함께 건드리는 일이라 이번에는
하지 않았다. 대신 테스트가 "이름과 달리 절대 경로"라고 명시한다.

## ⑥ 미리보기와 Plan이 달라지는 정상적인 경우

**미리보기는 source에 무엇이 있는지**를 세고, **Plan은 목적지에 무엇을 해야 하는지**를
계산한다. 이미 같은 파일이 있는 상태에서 다시 Convert하면:

- 미리보기 `games` = 1 (source 기준이라 그대로)
- Plan `added` = 1 (항목은 올라간다 — 파일은 같아도 **Metadata는 다를 수 있다**)
- Plan `addedBytes` ≠ 0 (예상 전송량)
- **capacity `deltaBytes` = 0** ← 실제로 늘어나는 디스크 사용량

용량 경고를 판단할 때 봐야 하는 것은 마지막 값이다. 이 구분을 테스트에 적어 뒀다.

## ⑦ Adapter 계약 테스트

`AdapterContractTests`가 **등록된 모든 Adapter를 훑는다.** Adapter가 늘 때마다 각자
테스트를 쓰기를 기대하면 언젠가 빠지므로, 새 Adapter도 자동으로 이 검사를 받게 했다.

- `supported_fields`가 공통 모델 안의 값들인가, 비어 있지 않은가, `name`을 담는가
- `media_types`에 중복이 없는가
- `tag_raw`/`raw_is_mine`이 출처를 제대로 다루는가(빈 값에는 표시를 붙이지 않는다)
- Pegasus만 `region`이 빠져 있는가 — 선언이 실제 포맷과 어긋나면 미리보기가 거짓말을 한다

## ⑧ 벤치마크 — **내가 보고한 우선순위가 틀렸다**

Phase 7.1·7.2에서 나는 "`write_index()`가 항목마다 불리는 O(n²)가 다음 과제"라고
적었다. 재 보니 **둘 다 틀렸다.**

### 규모별 실측

| | 1,000 게임 | 5,000 게임 |
|---|---|---|
| Scan | 0.29s | 1.24s |
| Convert 미리보기 | **0.04s** | **0.22s** |
| Convert → Plan | 0.28s | 1.47s |

미리보기와 Plan은 문제가 없다.

### Apply는 느리다 — 그러나 O(n²)가 아니다

| 게임 수 | Apply |
|---|---|
| 100 | 4.55s |
| 200 | 9.67s |
| 400 | 20.50s |

배가 될 때마다 2.1배 — **선형이되 항목당 상수가 약 50ms로 크다.** (1,000개면 약 50초,
5,000개면 4분대.)

### 그 50ms가 어디서 나오는지 갈라 봤다 (200게임 기준)

| | 시간 |
|---|---|
| 그대로 | 9.79s |
| **복사 호출만 제거** | **1.98s** |
| write_index만 제거 | 7.87s |

**복사가 80%, `write_index`가 20%다.** `_apply_add`가 항목마다
`file_ops.copy_files()`를 부르고, 그때마다 Robocopy 프로세스가 새로 뜬다 — 그 프로세스
기동 비용이 진짜 병목이다.

> **정정**: 앞선 두 리포트에서 "`write_index()` bulk화가 다음 과제"라고 적은 것은
> 근거가 약했다(재 보지 않고 O(n²)라고 단정했다). 실제로 먼저 고칠 것은
> **항목별 복사 호출을 System 단위로 묶는 것**이고, `write_index` bulk화는 그 다음이다.
> 둘 다 "항목마다 vs 묶어서"라는 같은 모양의 문제이므로, 되돌리기 정책을 한 번 정하면
> 함께 처리할 수 있다.
