# Phase 7.4 — 확정한 Match가 파일 rename에도 살아남게

**요약.** Phase 5에서 이월된 문제를 닫았다. `match_links`가 파일명을 키로 쓰기 때문에
사용자가 ROM 이름을 바꾸면 **직접 고른 Match가 조용히 끊겼다.**

파이썬 341개(신규 10개), Playwright 51개 전부 통과.

---

## 1. 왜 스키마를 다시 흔들지 않았는가

Phase 5에서 이 문제를 이월할 때 적은 이유는 "고치려면 Cache에 안정적인 rom key를
심어야 한다"였다. 다시 보니 **그럴 필요가 없었다** — Cache가 이미 `volume_file_id`를
들고 있다(`st_dev:st_ino`, 스캔할 때 채워진다).

Windows에서 실측:

```
rename 전 : 16306104620561437209:562949954555575
rename 후 : 16306104620561437209:562949954555575   ← 유지
내용 수정 후: (같음)                                ← 유지
새로 만든 파일: ...:844424931266231                 ← 다름
```

rename과 내용 수정에는 버티고 새 파일과는 구별된다. 필요한 성질을 정확히 갖고 있다.

---

## 2. 주 키를 바꾸지 않고 **보조 수단**으로 썼다

파일 ID를 주 키로 삼지 않은 이유:

- 네트워크 공유나 비NTFS에서는 **값이 없다**(`None`).
- 다른 볼륨으로 옮기면 **바뀐다**.

그래서 `(collection_id, system, filename)`을 그대로 주 키로 두고, 파일 ID는
`match_links`의 열로 함께 저장해서 두 가지에만 쓴다.

### ① 이름이 같아도 파일이 다르면 남남으로 본다

rename 뒤 **같은 이름의 다른 파일**이 생기면, 이름만 보고 옛 링크를 물려주게 된다.
저장된 파일 ID와 지금 파일의 ID가 둘 다 있는데 서로 다르면 그 링크는 이 파일의 것이
아니다. (테스트: `test_a_different_file_with_the_old_name_does_not_inherit_the_link`)

### ② 이름으로 못 찾으면 파일 ID로 되찾고, **그 자리에서 고쳐 놓는다**

되찾기만 하고 두면 그 뒤로도 매번 파일 ID로 뒤져야 한다. 찾은 김에 `filename`을 새
이름으로 갱신해서, 다음부터는 이름으로 바로 찾히게 한다(자가 복구).

파일 ID가 없으면(`None`) 예전과 똑같이 이름으로만 찾는다. **그 환경에서 rename하면
링크가 끊기는 것은 그대로**이고, 그때도 엉뚱한 항목에 붙지는 않는다는 것만 테스트로
고정했다.

---

## 3. 무엇을 검증했는가

| 테스트 | 지키는 것 |
|---|---|
| `test_the_link_survives_a_rename` | rename 후에도 사용자가 고른 Match가 유지된다 |
| `test_the_link_is_repaired_in_place` | 새 이름으로 고쳐진다(옛 이름은 남지 않는다) |
| `test_ingest_follows_the_renamed_link` | rename 후 Ingest가 **새 Identity를 만들지 않는다** |
| `test_a_different_file_with_the_old_name_...` | 옛 이름을 쓰는 새 파일이 남의 Match를 물려받지 않는다 |
| `test_without_a_file_id_it_behaves_as_before` | 파일 ID가 없는 환경에서의 동작을 명시 |
| `MatchLinkStoreTests` 4건 | 저장소 수준의 규칙(같은 이름 다른 파일 / 다른 이름 같은 파일 / Collection 범위 / 옛 링크 호환) |

세 번째가 실질적으로 가장 중요하다 — Match를 확정하는 이유가 "Ingest가 그 Identity에
붙게 하는 것"이므로, 링크가 끊기면 Archive에 중복 Identity가 생긴다.

### 테스트가 실제로 잡는지 확인했다

파일 ID 조회를 임시로 꺼 보니 **5개가 실패했다.** (Phase 7.1에서 배운 절차)

---

## 4. 남은 것

- **다른 볼륨으로 파일을 옮기면 링크가 끊긴다.** 파일 ID가 바뀌기 때문이다. 이건
  파일 ID 방식의 한계이고, 여기서 더 가려면 결국 해시가 필요하다 — 비용 때문에
  보류한 그 선택지다.
- Compare Row key 구조화(Phase 6에서 이월, 우선순위 낮음)와 Phase 8(MTP, 선택)이
  남는다.
