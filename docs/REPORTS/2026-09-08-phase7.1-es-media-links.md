# Phase 7.1 — EmulationStation Media Link을 Plan/Apply에 연결

**요약.** Phase 7이 남긴 구멍(Adapter만 있고 Apply에 연결 안 됨)을 닫았다. 연결하는
과정에서 **두 개의 실제 버그를 더 찾았고**, 그중 하나는 처음 만든 통합 테스트가
*우연히 통과하는 바람에* 하마터면 놓칠 뻔했다.

파이썬 292개(신규 16개), Playwright 45개 전부 통과.

---

## 1. 경계를 먼저 세웠다 — 계산과 쓰기의 분리

리뷰 권고대로 "무엇을 바꿀지"와 "실제로 쓰기"를 나눴다.

```
Adapter.build_media_links()   무엇을 어디에 둘지 계산만 한다 (파일 안 건드림)
        ↓
Apply: 파일 복사
        ↓
Adapter.write_media_links()   System 단위로 한 번만 기록
```

`FrontendAdapter`에 두 메서드를 기본 no-op으로 넣었다. ES-DE / Pegasus / LaunchBox는
**폴더 규칙**으로 media를 찾으므로 기록할 것이 없고, 원조 EmulationStation만 재정의한다.
덕분에 나중에 다른 Frontend가 같은 필요를 갖게 되어도 자리가 이미 있다.

### 여기서 Phase 7의 설계 실수 하나를 고쳤다

Phase 7에서 만든 `write_media_links(layout, filename, pairs)`는 **ROM 하나씩** 받는
형태였다. Apply에서 그대로 부르면 게임 1,000개에 gamelist.xml을 1,000번 다시 쓰게 된다 —
Adapter 계약 1이 애초에 막으려던 O(n²)가 그대로 재현되는 모양이었다. 지금은
`write_media_links(layout, links_by_filename)`로 System 단위 bulk다.

`media_pairs()`도 `build_media_links()` 위에 세워 두 계산이 갈라질 수 없게 했다.
복사되는 곳과 gamelist에 적히는 곳이 어긋나면 "파일은 있는데 화면엔 안 나온다"가 되는데,
그게 원조 ES에서 가장 잦은 사고다.

---

## 2. 연결하면서 찾은 버그 — source의 media 경로가 target으로 샜다

`frontend_raw`는 계약 2에 따라 미지 태그를 보존한다. 그런데 원조 ES의
`<thumbnail>`/`<video>`는 **경로**다. 다른 Collection으로 게임을 복사하면
`write_index()`가 그 경로를 target gamelist에 그대로 적어서, target이 **source의 폴더나
아무 데도 없는 곳**을 가리키게 된다.

계약 2를 깨지 않으면서 고치기 위해 개념을 하나 추가했다.

```python
FrontendAdapter.strip_location_raw(frontend_raw)   # 기본: 그대로
EmulationStationAdapter.strip_location_raw(...)    # media 경로 태그를 걷어낸다
```

"모르는 필드를 버리지 말라"는 계약은 유지하되, **그 자리에서만 참인 값**은 새 위치로
따라가지 않는다. 같은 Collection 안에서 다시 쓸 때는 호출하지 않으므로 제자리 보존은
그대로다.

---

## 3. 테스트가 우연히 통과했다 — 두 번 확인해서 잡았다

처음 만든 통합 테스트 11개가 **한 번에 전부 통과**했다. 그래서 수정을 임시로 되돌려
"이 테스트가 정말 이 수정을 검증하는가"를 확인했더니 — **11개 중 2개만 실패했다.**
핵심 통합 테스트가 수정 없이도 통과하고 있었다.

원인은 fixture였다. source와 target을 **둘 다 우리 layout 규칙**으로 만들어 두었기
때문에, source의 상대 경로(`../../media/ps2/...`)가 target에서도 우연히 해석됐다.
경로가 샜는데도 결과가 맞아떨어진 것이다.

fixture를 **RetroPie 스타일**(`downloaded_images/<system>/<stem>.png`)로 바꿨다 — 우리가
쓸 때 쓰는 배치와 다르므로, 경로를 베껴 적으면 target에서 깨진다. 그리고 target을 한
단계 더 깊은 곳에 두어 트리 모양도 다르게 했다.

다시 확인:

| | 수정 있음 | 수정 없음 |
|---|---|---|
| 처음 fixture | 11 통과 | **2 실패** (핵심 테스트가 그냥 통과) |
| 고친 fixture | 11 통과 | **6 실패** |

이 확인을 안 했다면 "테스트 11개 추가, 전부 통과"라고 보고하면서 실제로는 검증되지 않은
코드를 넘길 뻔했다.

## 4. 실패 처리

- **media 복사 실패** → 링크 단계에 아예 도달하지 않는다(기존 순서 그대로: 파일이
  자리를 잡은 뒤에 메타데이터). 테스트로 고정했다.
- **링크 기록 실패** → 그 System의 항목을 **PARTIAL로 내린다.** 파일은 복사됐지만
  Frontend가 못 찾는 상태이므로, 성공으로 처리해 Plan에서 지워버리면 사용자는 왜 media가
  안 보이는지 알 길이 없다. Plan에 남겨 다시 시도할 수 있게 한다.
- **복사되지 않은 media**는 링크로 적지 않는다. 실제로 존재하는 dest만 기록한다 —
  안 그러면 gamelist가 없는 파일을 가리킨다.

Cache는 Apply가 돌려주는 `systems`로 그 System만 다시 스캔하는 기존 경로를 그대로 타며,
`hasMedia`가 갱신되는 것까지 테스트로 확인했다.

---

## 5. 남은 것

Phase 7.2(Adapter 간 변환 UI)로 넘어가기 전에 알아둘 것 하나:

**`write_index()`가 여전히 항목 하나씩 호출된다.** `_apply_add`가 ADD 항목마다
`adapter.write_index(layout, [entry])`를 부르므로, media 링크에서 고친 것과 같은 O(n²)가
메타데이터 쪽에는 남아 있다. 이번에 함께 고치지 않은 이유는 **실패 처리의 단위가
바뀌기 때문**이다 — 지금은 항목 하나가 실패하면 그 항목의 파일만 되돌리는데, bulk로
묶으면 그 경계가 사라진다. 되돌리기 정책을 먼저 정해야 하는 일이라 별도로 다뤄야 한다.
