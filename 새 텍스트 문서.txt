봤다. 이번에는 단순히 커밋 메시지를 읽은 게 아니라 **현재 `main`의 Phase 3 핵심 구현부를 실제 코드 수준에서 대조해서 봤다.**

결론부터 말하면:

> **전체 방향은 상당히 좋다. 하지만 지금 상태에서 Phase 4 Archive로 넘어가면 안 된다.**
>
> 특히 **Apply의 실패 복구, 파일 충돌, Storage 이동의 원자성, Cache 동기화** 쪽에 실제 데이터 손실/불일치를 만들 수 있는 문제가 있다.

현재 HEAD는 `de1ee0e7...`이고, Phase 3 구현 자체는 `Plan → Validator → Applier → FileOperationEngine`으로 꽤 잘 분리되어 있다. `Plan`도 실제 파일을 건드리지 않고 Storage별 delta를 O(1)로 누적하도록 되어 있다.

아래는 중요도 순서대로 본 것이다.

# 1. 가장 심각함 — Storage 이동 실패 시 DB와 실제 파일이 불일치할 수 있다

현재 `_apply_storage_change()`의 흐름이:

```text
현재 registry
    ↓
old_layout 계산
    ↓
메모리에서 storage_id 임시 변경
    ↓
new_layout 계산
    ↓
ROM 파일 실제 이동
    ↓
registry.move_system()
```

이다.

문제는 **파일 이동 성공 후 `registry.move_system()`이 실패하는 경우**다.

예를 들어:

```text
Internal/ps2/
    game1.iso
    game2.iso

External/ps2/
    없음
```

에서 Apply.

파일 이동:

```text
Internal/ps2/game1.iso
        ↓
External/ps2/game1.iso

Internal/ps2/game2.iso
        ↓
External/ps2/game2.iso
```

까지 성공했다.

그런데:

```python
registry.move_system(...)
```

에서 DB lock이나 SQLite 오류가 발생하면?

실제 상태:

```text
파일: External
Registry: Internal
```

이 된다.

그 순간 앱을 다시 열면 **Registry는 Internal이라고 믿는데 실제 ROM은 External에 있다.**

이건 Phase 3에서 가장 먼저 해결해야 할 문제다.

### 더 나쁜 점

현재 코드는 파일 이동이 실패하면:

```python
entry.status = "failed"
```

하고 끝난다.

하지만 **일부 파일만 이동된 경우**도 고려해야 한다.

예:

```text
100개 ROM 이동
97개 성공
3개 실패
```

이면 97개는 이미 새 위치에 있다.

그런데 Registry는 변경하지 않는다.

즉:

```text
Registry: Internal
실제:
  97개 External
   3개 Internal
```

이라는 더 심각한 상태가 가능하다.

### 권장 수정

Storage Change는 사실상 별도의 transaction으로 봐야 한다.

최소한:

```text
1. destination 검사
2. source 검사
3. collision 검사
4. registry lock
5. filesystem move
6. 성공 확인
7. registry 변경
8. cache 갱신
9. 실패 시 recovery
```

구조가 필요하다.

그리고 **부분 이동을 실패로만 기록하고 끝내면 안 된다.**

가능하면:

```text
move
 ↓
verify
 ↓
registry update
 ↓
cache update
```

중 하나가 실패하면 이전 단계로 되돌리는 recovery가 필요하다.

# 2. 매우 심각 — 기존 파일과의 충돌을 Plan에서 제대로 막지 않는다

`plan_add()`를 보면 대상에 동일한 파일이 있으면:

```python
existing = provider.stat(dest)

0 if existing and existing.size == size else size
```

로 계산한다.

이건 **용량 계산 관점에서는 이해할 수 있지만, 파일 안전성 관점에서는 위험하다.**

예를 들어:

```text
Source:
Super Mario.zip
100 MB

Destination:
Super Mario.zip
100 MB
```

현재 Plan은:

```text
physical_delta = 0
```

이다.

그런데 실제 Apply에서는 그냥:

```python
pairs.append((source, destination))
file_ops.copy_files(...)
```

한다.

즉:

> **같은 크기라는 이유만으로 기존 파일을 덮어쓸 가능성이 있다.**

같은 크기 ≠ 같은 파일이다.

특히 ROM 관리 프로그램에서는:

```text
같은 이름
같은 크기
다른 CRC
```

가 충분히 가능하다.

### 이건 반드시 정책을 정해야 한다

나는 다음을 권장한다.

| 상황                          | 처리           |
| --------------------------- | ------------ |
| 동일 path + 동일 identity       | Skip         |
| 동일 path + 동일 hash           | Skip         |
| 동일 path + 다른 hash           | **Conflict** |
| 동일 path + hash 없음 + 동일 size | 확인 필요        |
| 이름 다름                       | 정상 copy      |

즉 `physical_delta == 0`과 `copy하지 않아도 됨`은 같은 개념이 아니다.

**용량 계산과 파일 충돌 판정을 분리해야 한다.**

# 3. Storage 이동에도 동일한 충돌 문제가 있다

`move_pairs()`는 동일 파일명인 경우 Robocopy `/MOV`를 사용한다.

예:

```text
INTERNAL
 └─ PS2
     └─ Game.iso

EXTERNAL
 └─ PS2
     └─ Game.iso
```

상태에서 PS2 전체를 이동하면 어떻게 할 것인가?

현재 설계에는 **destination collision policy가 없다.**

특히 `/MOV`는 단순한 "안전한 이동"이라는 의미가 아니다.

destination에 동일 파일명이 있으면 **원본을 어떻게 처리할 것인지 명확한 정책이 필요하다.**

이건 Plan 단계에서 보여줘야 한다.

예:

```text
PS2 → EXTERNAL

12 files
11 movable
1 conflict

[Apply]

❌ Game.iso
   destination already exists
```

그리고 사용자가 선택:

```text
Skip
Overwrite
Rename
Cancel
```

정책이 필요하다.

# 4. 더 중요한 문제 — Apply가 "전체 transaction"이 아니다

현재 Apply는:

```python
for entry in adds:
    _apply_add(...)

for entry in deletes:
    _apply_delete(...)

for entry in moves:
    _apply_storage_change(...)
```

형태다.

즉:

```text
ADD 1 성공
ADD 2 성공
ADD 3 실패
ADD 4 성공
...
DELETE 1
DELETE 2
MOVE ...
```

가 가능하다.

이 자체가 반드시 잘못된 건 아니다.

오히려 네가 설계한

> "문제 있는 항목만 실패하고 나머지는 진행"

정책과는 맞는다.

그런데 UI/사용자 관점에서 중요한 문제가 있다.

현재 사용자가 보는:

```text
Plan: 125 changes
```

가 Apply 후:

```text
118 applied
7 failed
```

가 된다.

이때 **실패한 7개가 Plan에 남는지, 제거되는지**가 명확해야 한다.

현재는 성공한 것만:

```python
plan.remove(entry.key)
```

한다.

그래서 실패 항목은 Plan에 남는다.

이건 나쁘지 않다.

하지만 UI가 반드시:

```text
Applied: 118
Failed: 7

7 items remain in Plan
```

이라고 명확히 보여줘야 한다.

그렇지 않으면 사용자는 "Apply 했으니 끝났다"고 생각할 수 있다.

# 5. `ADD`에서 Metadata 기록 실패 시 이미 복사된 파일이 남는다

이것도 중요하다.

현재:

```text
파일 copy
    ↓
metadata write
```

순서다.

이 순서 자체는 맞다.

하지만 metadata write가 실패하면:

```text
ROM: 있음
media: 있음
gamelist: 없음
```

이 된다.

현재 코드는:

```python
entry.status = "failed"
```

하고 끝난다.

즉 실제 filesystem에는 이미 파일이 존재한다.

그런데 Plan에는 실패로 남는다.

다음 Apply에서 다시 실행하면:

```text
이미 존재하는 ROM
+
이미 존재하는 media
```

를 다시 처리하게 될 수 있다.

### 더 좋은 구조

ADD는:

```text
copy
 ↓
verify
 ↓
metadata write
 ↓
verify
 ↓
success
```

로 보고,

metadata write 실패 시:

```text
rollback copied files
```

를 시도해야 한다.

최소한:

```text
FAILED
Filesystem partially applied
```

라는 상태는 구별해야 한다.

# 6. DELETE 구현은 현재 상당히 애매하다

이 부분은 코드 주석 자체가 사실상 문제를 인정하고 있다.

현재 `_apply_delete()`는:

```text
ROM 삭제
Media 삭제
```

까지만 한다.

그리고:

> gamelist 항목 제거는 Cleanup 기능에서 다룬다

라고 되어 있다.

이건 **제품 의미를 다시 확정해야 한다.**

사용자가 Gamelist에서 게임을 선택하고:

```text
Delete
```

했을 때 기대하는 것은 일반적으로:

```text
ROM 삭제
Media 삭제
Metadata 삭제
```

다.

그런데 현재는:

```text
ROM 없음
Media 없음
gamelist에는 게임 존재
```

가 된다.

다음 스캔에서는 어떻게 되는가?

결국 metadata-only game으로 남을 가능성이 있다.

이건 "Cleanup"과 "Delete Game"을 명확히 분리해야 한다.

나는 다음처럼 하는 걸 권장한다.

### Delete Game

```text
ROM
Media
Gamelist entry
```

전부 제거.

### Remove ROM

```text
ROM만 제거
```

metadata는 유지.

### Cleanup

```text
orphan media
orphan metadata
broken entries
```

정리.

현재 구현은 이 세 개가 섞여 있다.

# 7. DELETE의 Cache도 즉시 갱신되지 않는다

실제 파일을 삭제했는데 Cache는 기존 row를 가지고 있다.

즉:

```text
Filesystem
    ↓ delete
파일 없음

Cache
    ↓
파일 있음
```

상태가 된다.

현재 Apply 코드에서는 delete 이후 Cache 업데이트가 보이지 않는다.

따라서 Apply 직후 UI가 Cache 기반이라면:

```text
게임이 여전히 보임
용량도 예전 값
Status도 이상
```

이런 현상이 발생할 수 있다.

Phase 3에서 반드시:

```text
Apply
 ↓
Cache delta/update
 ↓
UI refresh
```

를 정의해야 한다.

전체 Full Scan을 다시 돌리는 것은 비효율적이다.

# 8. ADD도 Cache 갱신 문제가 있다

반대도 마찬가지다.

ADD:

```text
filesystem copy
metadata write
```

했는데 Cache에는 아직 없다.

따라서:

```text
Actual
```

과 실제 filesystem이 일시적으로 다를 수 있다.

특히 사용자가 Apply 직후:

```text
Search
Sort
Filter
Capacity
```

를 하면 Cache 기준 결과가 나올 가능성이 있다.

따라서 Apply 성공 시 Cache에 최소한:

```text
ROM row
metadata
media
size
mtime
present
```

를 반영하는 것이 좋다.

# 9. `validate()`의 DELETE 검증이 너무 약하다

현재 DELETE 검증은:

```python
if cache.get_row(entry.rom_uid) is None:
    invalid
```

뿐이다.

문제는 Plan 생성 후 실제 파일이 바뀌어도 Cache row 자체가 존재하면 통과할 수 있다는 것이다.

예:

```text
Plan:
Game.iso 1GB 삭제

그 사이 외부에서:
Game.iso 교체
```

Cache:

```text
Game.iso 존재
size=1GB
```

이면 통과할 가능성이 있다.

DELETE도 ADD처럼 최소한:

```text
exists
size
mtime
```

또는 더 좋게:

```text
identity/hash
```

검증이 필요하다.

# 10. Capacity 계산도 "현재 파일"과 "Plan"의 의미가 조금 섞여 있다

현재:

```python
actual = cache.storage_usage()
delta = plan.delta()
planned = actual + delta
```

다.

계산 자체는 깔끔하다.

그런데 앞서 말한 collision 때문에:

```text
existing same filename
existing size = 500MB
new file = 700MB
```

실제 변화는:

```text
+200MB
```

인데 현재는:

```text
+700MB
```

로 계산될 가능성이 있다.

반대로 동일 파일을 덮어쓰는 것이 허용되지 않아야 한다면:

```text
Conflict
```

여야 한다.

따라서 Capacity 계산 전에 **filesystem conflict resolution**이 먼저 확정되어야 한다.

# 11. Robocopy 구현에도 하나 중요한 위험이 있다

`_copy()`에서 Robocopy return code를 상당히 의존하고 있는데, 최종 성공 판정은:

```python
results[str(dest)] = dest.exists()
```

다.

이건 단순하고 좋은 장점이 있지만:

```text
dest exists
```

만으로 성공을 판단하면 안 되는 경우가 있다.

예:

```text
기존 destination 존재
copy 실패
```

여도:

```text
dest.exists() == True
```

가 될 수 있다.

즉:

> **기존 파일이 존재하는 것과 이번 copy가 성공한 것은 다르다.**

이것 역시 destination collision 문제와 연결된다.

최소한:

```text
before stat
after stat
robocopy exit code
after size
```

를 조합해서 판단해야 한다.

# 12. `move_pairs()`도 `dest.exists()`만으로 성공 판정

동일하다.

현재:

```python
_run(robocopy ...)
results[str(dest)] = dest.exists()
```

이다.

destination이 이미 있었는데 move가 실패해도:

```text
dest.exists() = True
```

가 된다.

따라서 **이건 실제 버그 후보**다.

특히 Storage 이동에서는 치명적이다.

### 최소 개선

이동 전:

```text
source exists
destination state
source size
```

를 저장하고,

이동 후:

```text
source absent
destination exists
destination size == source size
```

를 확인해야 한다.

---

# 13. `copy_files()`의 디렉터리 생성 실패 처리도 실제 결과와 연결해서 봐야 한다

Robocopy 쪽은 `_ensure_dir()` 실패를 처리하도록 개선됐다. 이건 좋은 수정이다.

다만:

```python
for directory in extra_dirs:
    _ensure_dir(directory)
```

에서 return 값을 무시한다.

즉 `extra_dirs` 생성 실패를 먼저 발견하지 못하고 이후 `_copy()`에서 다시 판단할 수 있는 구조다.

큰 버그는 아니지만:

```text
prepare destination
→ failure
→ 모든 관련 pair 실패
```

로 명시적으로 만드는 편이 낫다.

형태다.

하지만 나중에:

```text
NAS

MTP

removable SD
```

로 확장하면 문제가 된다.

예:

```text
Collection A
E:\ROM\PS2

Collection B
\\NAS\ROM\PS2
```

정도는 괜찮지만,


에서는 일반적인 Windows absolute path로 표현할 수 없다.

# 15. Plan 자체는 상당히 잘 만들었다

여기서는 반대로 좋은 점을 명확히 말하겠다.

`Plan` 모델은 방향이 좋다.

특히:

```python
self._entries
self._delta
```

를 가지고 있고 entry를 교체할 때 기존 delta를 빼고 새 delta를 넣는다.

따라서:

```text
10,000 ROM
```

을 Plan에 넣으면서 매번 Collection 전체를 다시 계산하지 않는다.

이건 네가 원했던:

> 수천 개를 붙여넣어도 빠르게 동작

이라는 요구에 정확히 맞는다.

# 16. `PlanEntry.key`는 향후 반드시 손봐야 할 가능성이 있다

현재:

```python
ADD|system|filename
DELETE|system|filename
STORAGE_CHANGE|system
```

이다.

문제는 **filename이 identity가 아니라는 것**이다.

Retro game 관리에서는:

```text
Game A
    filename = "Game.zip"

Game B
    filename = "Game.zip"
```

같은 상황이 Collection 간에는 충분히 발생할 수 있다.

특히 앞으로 Archive/Game/ROM identity가 본격적으로 들어오면:

```text
rom_uid
game_id
```

중 하나를 Plan identity로 사용하는 게 더 안전하다.

현재 `rom_uid`가 이미 존재하므로:

```text
ADD:
source Collection ID + ROM identity + destination system

DELETE:
rom_uid

MOVE:
system identity
```

같은 구조를 검토하는 게 좋다.

Phase 3에서 반드시 전면 수정할 필요는 없지만 **Phase 5 Match 전에 정리하는 게 좋다.**

# 17. ES-DE Adapter의 media matching은 주의해서 봐야 한다

현재:

```python
stem = Path(filename).stem
...
f"{stem}{suffix}"
```

으로 media destination을 만든다.

ES-DE 특성상 상당히 자연스럽다.

하지만:

```text
Game.iso
Game.cue
Game.bin
```

같은 multi-file / multi-disc 구조에서는:

```text
Game.png
```

가 어느 ROM에 대응하는지 identity 문제가 생긴다.

특히 앞으로 Multi-disc 지원을 할 거라면:

```text
Game (Disc 1).cue
Game (Disc 2).cue
```

같은 naming convention과 Game identity를 분리해서 생각해야 한다.

**Phase 3에서 해결할 필요는 없지만 Phase 5 Match 전에 반드시 설계해야 한다.**

## 특히 Claude Code에 다음 작업을 시키는 게 좋다

현재 자동화 프롬프트를 그대로 돌리기보다는 다음과 같은 **Phase 3 hardening 작업**을 한 번 거치는 게 좋다.

핵심 요구는:

```text
Do not start Phase 4 yet.

Harden the existing Phase 3 implementation.

Priority:
1. destination collision detection
2. safe copy/move verification
3. Storage Change transactional behavior and recovery
4. ADD rollback on metadata failure
5. DELETE filesystem/cache consistency
6. post-Apply cache synchronization
7. validate actual filesystem state immediately before mutation
8. preserve the existing Plan architecture
9. do not redesign Metadata/Media/ROM UI
10. add filesystem-level failure injection tests

Do not merely add tests to match the existing implementation.
First identify real failure modes, then fix the implementation, then add tests.
```

이 방향이 맞다.

**현재 코드에서 가장 위험한 것은 "기능이 없다"가 아니다.
"정상 상황에서는 잘 되는데 예외 상황에서 DB와 실제 ROM 상태가 서로 달라질 수 있다"는 점이다.**

Retro ROM 관리 프로그램에서는 이게 UI 버그보다 훨씬 중요하다. 파일을 잃으면 복구가 어렵기 때문이다.

현재 `main`을 기준으로 보면 **아키텍처 자체를 갈아엎을 이유는 전혀 없다.** 오히려 지금까지 만든 구조는 유지하고, Phase 3를 **"실패해도 데이터가 망가지지 않는 수준"까지 단단하게 만드는 것**이 다음 작업이다.
